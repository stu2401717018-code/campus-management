# Контейнеризация и оркестрация

В този проект използваме Docker за контейнеризация на три основни компонента:

### 1. Базов образ (base image)

Първо създаваме базов Docker образ (`campus/base:1.0`), който съдържа общите зависимости за всички услуги:
- Java 17 runtime
- Общи системни инструменти (curl, bash, wget)
- Настройки за времева зона
- appgroup и appuser за по-добра сигурност

Този базов образ се използва като основа за всички останали сървиси. Това ни позволява да:
- Избягваме дублиране на код в различните Dockerfile-и
- Поддържаме консистентност между сървисите
- Лесно да актуализираме общите зависимости на едно място

### 2. Публично приложение (app-public)

Това е публичното API, което приема HTTP заявки от клиенти. Характеристики:
- **Публикуван порт**: Достъпно на `localhost:8080` от хоста
- **Мрежа**: Свързано към `public` и `internal` мрежите
- **Функционалност**: REST API за управление на студенти, курсове, катедри и т.н.
- **Взаимодействие**: Извиква `app-internal` през вътрешната мрежа за обработка на данни

### 3. Вътрешно приложение (app-internal)

Това е вътрешен сървис, който работи само в защитената мрежа. Характеристики:
- **Няма публикуван порт**: Не може да се достъпи директно от хоста
- **Мрежа**: Само в `internal` мрежата
- **Функционалност**: Обработва данни, нормализира и валидира информация
- **Логове**: Записва логове в именуван volume (`app_internal_logs`), който се запазва след рестарт на контейнера

## Dockerfile структура

### Базов Dockerfile (base/Dockerfile)

```dockerfile
ARG JAVA_VERSION=17
FROM eclipse-temurin:${JAVA_VERSION}-jdk-alpine AS base
```

Използваме `ARG` за да можем да подаваме версията на Java при build време. Това прави образа по-гъвкав.

### Dockerfile на сървисите

Всеки сървис има собствен Dockerfile, който:
1. Използва базовия образ: `FROM campus/base:1.0`
    ```dockerfile
    FROM campus/base:1.0
    ```
2. Използва `ARG`* за build-time параметри (например версия на Java)
    ```dockerfile
    FROM campus/base:1.0
    ```
3. Използва `ENV`* за runtime променливи (например порт, път за логове)
    ```dockerfile
    FROM campus/base:1.0
    ```
4. Изгражда приложението (multi-stage build за по-малък финален образ)
5. Конфигурира health checks за мониторинг

   * `ARG`: Използва се по време на build процеса. Не е достъпно в runtime.
   * `ENV`: Използва се в runtime. Достъпно е в контейнера след стартиране.

## Docker Compose оркестрация

Docker Compose ни позволява да дефинираме и управляваме множество контейнери като единна система.

### Мрежи (Networks)

**public мрежа:**
- Достъпна от хоста
- Само `app-public` е свързано към нея
- Позволява на клиентите да достъпват публичното API

**internal мрежа:**
- Изолирана мрежа, недостъпна от хоста
- Всички сървиси (app-public, app-internal, postgres) са свързани към нея
- Позволява на сървисите да комуникират помежду си безопасно

### Volumes (томове)

**app_internal_logs:**
- Именуван volume за запазване на логове
- Монтиран в `/var/log/app` в контейнера на app-internal
- Логовете се запазват дори след изтриване на контейнера
- Полезно за debugging и мониторинг

**postgres_data:**
- Именуван volume за данните на PostgreSQL
- Запазва базата данни между рестарти

### Health Checks

Всеки сървис има health check, който проверява дали сървисът работи правилно:
- **postgres**: Проверява с `pg_isready`
- **app-public**: Проверява `/actuator/health` endpoint
- **app-internal**: Проверява `/api/health` endpoint

Сървисите използват `depends_on` с `condition: service_healthy`, за да гарантират че зависимите сървиси са готови преди стартиране.

### Мащабиране (Scaling)

Можем да стартираме множество инстанции на `app-public`:

```bash
docker-compose up --scale app-public=2
```

Това създава 2 контейнера на app-public, които споделят една и съща мрежа и могат да обработват заявки паралелно. Docker Compose автоматично балансира заявките между инстанциите.

## Предимства на тази архитектура

1. **Сигурност**: Вътрешните сървиси не са достъпни отвън
2. **Модулярност**: Всеки сървис може да се развива независимо
3. **Мащабиране**: Лесно добавяне на повече инстанции при нужда
4. **Персистентност**: Логове и данни се запазват между рестарти
5. **Изолация**: Проблеми в един сървис не засягат другите

## Как работи потокът на заявките

1. Клиент изпраща HTTP заявка към `http://localhost:8080/api/reports/process`
2. `app-public` получава заявката през публичната мрежа
3. `app-public` извиква `app-internal` през вътрешната мрежа: `http://app-internal:8081/api/process`
4. `app-internal` обработва данните и записва логове в volume-а
5. `app-internal` връща резултат на `app-public`
6. `app-public` комбинира резултата и го връща на клиента

Важно: Клиентът никога не може да достъпи `app-internal` директно, защото няма публикуван порт и е само в вътрешната мрежа.
